# Синхронизация: журнал как курсор, SignalR-push, офлайн-очередь, LWW

Данные пользователя синхронизируются между сервером и всеми его вкладками и устройствами без перезагрузки и без сети. Источником изменений служит уже существующий журнал (`changesets`), а не отдельная версия объектов: у набора есть сквозной номер `seq`, курсор клиента — `seq` последнего известного набора. Правки уходят пакетами, приходят push-сообщениями SignalR в формате догона, без сети копятся в очереди в IndexedDB. Конфликт правок решает «последняя запись побеждает» (LWW), строгими остаются только структурные инварианты. Решение опирается на ADR 0001 (логика на клиенте, сервер — хранилище с проверками) и ADR 0003 (скрытие отключённых расширений на сервере).

## Как устроено

**Сервер.**
- `changesets.seq bigint generated always as identity`. Набор применяется в своей транзакции под `pg_advisory_xact_lock` по пользователю, поэтому внутри области видимости порядок `seq` совпадает с порядком фиксации и курсор не проскочит незафиксированный набор. `seq` глобальный: у одного пользователя он идёт с дырами, поэтому итог набора несёт ещё `prevSeq` — курсор предыдущего набора того же пользователя, прочитанный под той же блокировкой. Клиент сдвигает курсор по своему подтверждению, только если `prevSeq` равен его курсору; иначе между ними наборы других вкладок, и курсор догонит push или догон.
- `id` набора генерирует клиент (UUIDv7). Повтор известного `id` ничего не применяет и возвращает `duplicate` с прежним `seq`; отклонённый набор не запоминается. По `id` клиент узнаёт своё эхо в push.
- LWW: у `update` и `move` «было» не сверяется, в журнал пишется фактическое старое значение. Отказ набора целиком — только при нарушении структуры: нет объекта или родителя, родитель недопустим по `allowedChildren`, цикл, singleton, расширение отключено, у удаляемого есть дети вне набора, `create` с существующим `id`.
- `POST /api/changesets` принимает пакет `{ changesets: [{ id, operations }] }`, каждый набор применяется независимо; ответ всегда 200 — `[{ id, status: applied | duplicate | rejected, seq?, prevSeq?, code?, detail? }]`. 4xx — только формат и авторизация. Набор, который не принимает БД (SQLSTATE класса 22 или 23 — неверное значение, нарушение ограничения, `id` набора, одновременно занятый другим пользователем), отклоняется с кодом `invalid_data`, а не даёт 5xx: иначе клиент повторял бы его вечно и очередь стояла бы. Сбои соединения и прочие ошибки по-прежнему 5xx.
- Полная загрузка — `GET /api/snapshot` → `{ seq, types, objects }` в одной транзакции `repeatable read`. Догон — `GET /api/changes?since=N` → `{ toSeq, changesetIds, upserts, deletes }` с финальным состоянием затронутых объектов; объекты, скрытые отключённым расширением, попадают в `deletes`. Если наборов после `N` больше `Sync:ResyncThreshold` (5000) или курсор новее журнала (БД пересоздана) — `{ resync: true }`.
- Push — хаб `/api/sync`. Диспетчер (`IChangeNotifier`) учитывает соединения каждого пользователя и отправляет каждому отдельно, со своим курсором. После фиксации набора соединения пользователя помечаются; первое уведомление открывает окно `Sync:PushWindow` (100 мс), по нему диспетчер читает журнал из БД после курсора соединения (один раз на курсор) и отправляет `changes` — формат догона плюс `fromSeq` (первое сообщение после подключения начинается с `prevSeq` набора), чтобы клиент увидел разрыв. Источник истины — БД, реализация внутри процесса. Подключение и отключение расширения рассылается как `resync`. Медленное соединение (предыдущая отправка ему не завершилась) пропускает окна и копит курсор, остальные вкладки получают поток дальше; освободившись, оно получает накопленное одним сообщением, а при превышении порога — `resync`. Неудачная отправка соединению заменяется `resync` в следующем окне.
- JWT для хаба передаётся в query `access_token` и читается только на пути хаба.

**Клиент.**
- Хранилище из двух слоёв: подтверждённое состояние (до курсора) и очередь неподтверждённых наборов. Входящие изменения применяются к подтверждённому слою, затем очередь накладывается заново записанными операциями, без хуков. Набор, ставший структурно невалидным, удаляется из очереди вместе с зависящими от него, пользователь получает одно сводное уведомление. Проверка — общим кодом контракта (`checkChangeset`), тем же, что в `fakeApi`.
- Итог действия локальный: `await data.setProperty(...)` разрешается после применения и постановки в очередь. Поздний отказ сервера — откат с каскадом и уведомление. Кому нужен итог сервера (например, `ensureStart` расширений ради `singleton_exists`), передаёт `confirmed: true`.
- SyncEngine отправляет очередь пакетами: окно 200 мс от первой правки (не debounce), не больше одного запроса в полёте, не больше 500 операций в запросе. Сеть, 5xx, 408, 429, 401 (истёкший вход) и ответ неверной формы повторяются с задержкой 1 с · 2^n до 30 с, очередь сохраняется; прочие 4xx отклоняют наборы пакета. После каждого соединения push и при разрыве курсора — догон; по `resync` сначала отправляется вся очередь (снимок не несёт `changesetIds`, иначе применённое повторилось бы), затем снимок, затем очередь переналагается. После `resync` по сигналу сервера вкладка перечитывает и каталог расширений с их регистрациями.
- Офлайн: база IndexedDB на пользователя — снимок, каталог расширений и очередь каждой вкладки (`tabId` новый на каждую загрузку страницы). Снимок пишет вкладка, только если её `seq` больше сохранённого. Очередь закрытой вкладки (отпущен Web Lock) подхватывает открытая. Старт из кэша, затем догон. Без сети при обновлении входа работа продолжается локально; после входа тем же пользователем очередь уходит. Выход с непустой очередью предупреждает (на время предупреждения отправка очереди приостановлена, чтобы число в нём не разошлось с потерянным) и удаляет базу. Данные из IndexedDB, ответы сервера и сообщения push проверяются по форме: испорченный кэш считается отсутствующим, неверное сообщение push — сигналом `resync`. Оболочку приложения кэширует service worker, `/api` он не перехватывает.
- Индикатор в шапке показывает «синхронизировано», «N неотправленных» (все вкладки), «офлайн» или «ошибка» по состоянию связи SyncEngine; предупреждения на `beforeunload` нет — очередь переживает закрытие вкладки.

## Considered Options

- **Версия у каждого объекта** (`objects.version`) и выборка «изменилось после». Отвергнуто: удаления пришлось бы хранить отдельно, а журнал уже содержит всё, включая удаления со снимком.
- **Оптимистичная блокировка по «было»** (отказ при несовпадении). Отвергнуто: при офлайне и нескольких вкладках отказы стали бы частыми, а пользователь не может осмысленно их разрешить; текст без слияния всё равно теряет одну из правок. Отмену защищает клиентская сверка: undo не затирает чужое значение.
- **Push только сигналом «есть новое»** с последующим догоном. Отвергнуто: лишний запрос на каждую правку; формат догона в самом сообщении позволяет применить его сразу, а `fromSeq` ловит пропуски.
- **`LISTEN/NOTIFY` или Redis** уже сейчас. Отложено: сервер один; диспетчер за интерфейсом `IChangeNotifier` заменяем.
- **Ждать подтверждения сервера в каждом действии.** Отвергнуто: без сети действия бы висели; итог локальный, а `confirmed: true` оставлен для редких случаев.

## Consequences

- Отказ набора бывает только структурным, и клиент обязан уметь откатывать уже показанные правки каскадом.
- Хуки выполняются один раз — когда пользователь совершает действие; при переналожении применяются записанные операции, поэтому логика хуков не должна зависеть от того, что видит другой клиент.
- Структура данных расширений по-прежнему меняется без миграций: после обновления сервера кэш клиента сбрасывает `resync` (курсор новее журнала).
- Курсор и `seq` будут переходить с пользователя на рабочее пространство вместе с учётом соединений и блокировкой.
- Снимок в кэше обновляется только при росте `seq`: смена типов без нового набора (подключение расширения) попадёт в кэш со следующим набором.
