# Команды объявляются в манифесте, код — на клиенте, пользовательские команды хранятся как объекты

Команда (автоматизация, не привязанная к выбранному объекту) описывается данными в манифесте расширения (`commands`: идентификатор, название, значок, параметры), а её код регистрируется на клиенте по идентификатору, как и код действий (ADR 0001). Команды, которые создаёт пользователь (например, быстрый доступ к заметке), — скрытые объекты платформенного типа «Пользовательская команда»: ссылка на команду-шаблон расширения и сохранённые значения параметров. Понятие «Механизм» (скрытый объект ради действий во вкладке «Автоматизация») отменяется.

## Considered Options

- Команды только в клиентском дескрипторе расширения. Отвергнуто: будущий конструктор расширений должен править команды как данные, а не код.
- Отдельный скрытый тип у расширения для каждой разновидности динамических команд (как `QuickAccessEntry`). Отвергнуто: дублирует один и тот же механизм «команда с сохранёнными параметрами» в каждом расширении.

## Consequences

- Сервер валидирует `commands` (уникальность `id`, параметры) и отдаёт их с каталогом расширений; без клиентского кода команда не выполнится.
- Пользовательская команда принадлежит расширению: панель скрывает её вместе с отключённым расширением, сервер при этом тип считает платформенным.
- Хуки расширения (переименование цели, удаление цели) отвечают за согласованность пользовательских команд со своими целями.
- Порядок кнопок блока расширения на панели задаёт номер объекта. Команда манифеста номера не имеет, поэтому первая перестановка в блоке «материализует» все его команды манифеста: создаются `CustomCommand` с `command` команды, пустыми `name` и `params` (подпись и значок берутся из манифеста, параметры спрашиваются диалогом) и номерами по порядку, а оригинал скрывается. Это же основа будущего переопределения команд манифеста.
