# 03: Контрактные сценарии Набора изменений для `fakeApi` и сервера

**What to build:** Один набор сценариев проверяет правила Набора изменений и в `fakeApi`, и на реальном сервере, чтобы клиентский тест не проходил там, где сервер откажет.

**Blocked by:** —

**Status:** ready-for-agent

- [ ] Формат сценария: языконезависимый JSON (начальное состояние типов и Объектов, Набор изменений, ожидаемый признак успеха и код ошибки там, где он есть); общая папка сценариев, доступная клиентским и серверным тестам
- [ ] Сценарии: допустимый родитель (`EnsureParentAllowsChild`), singleton (`EnsureSingletonAsync`), отключённое расширение (`extension_disabled`, `EnsureEnabled`), проверка значения (вид свойства, ссылка, `targetTypes`; `ValidateValueAsync`), проверка «было» (ADR 0001)
- [ ] Vitest: раннер сценариев против `fakeApi`; xUnit: раннер против реального сервера (Testcontainers)
- [ ] Сравнение по успеху и коду ошибки, не по тексту
- [ ] Расхождения устранены в `fakeApi` (`PLATFORM_TYPES` сверен с миграциями `0023`, `0024`); если сценарий требует правила, которого нет в `fakeApi`, оно добавляется туда
- [ ] Если сценарии покажут, что правила `ChangesetService` нельзя проверить без SQL, вынос в чистый module оформить отдельным тикетом, а не делать здесь
- [ ] `dotnet test Nimrata.Core.slnx`, `npm test`, `npm run lint`; записи в `CHANGELOG.md` клиента и сервера
