# Пилот Nimrata: ядро платформы и модуль Трекер

## Problem Statement

Я много лет разрабатывал платформу автоматизации Iris (.NET + WPF). Она устарела по стеку и интерфейсу: десктоп-клиент, ручная синхронизация, бизнес-логика на Lua внутри ядра, ограниченная расширяемость. Мне и моим коллегам нужна современная веб-платформа, на которой удобно автоматизировать рабочие задачи, и первое приложение на ней — личный трекер задач и заметок (как на Iris). Нужно проверить, что новая архитектура работает, прежде чем переносить на неё остальное.

## Solution

Новая веб-платформа Nimrata (ASP.NET Core + React/TypeScript + Postgres) и её первый модуль Трекер. Платформа хранит данные в виде типов и объектов в дереве, ведёт журнал изменений, даёт универсальные UI-компоненты (дерево, таблица свойств, контейнер вкладок, главное меню). Вся бизнес-логика модулей выполняется на клиенте на TypeScript (ADR 0001), сервер — общий слой хранения, проверок и журнала. Пользователь входит в систему, видит три панели (дерево слева, таблица свойств справа, вкладки по центру), работает со своими задачами и заметками, отменяет и повторяет действия, смотрит журнал изменений.

## Implementation Decisions

**Продукт и границы**
- Nimrata — веб-платформа, преемник Iris. Пилот: ядро плюс модуль Трекер. Только веб, без офлайна и десктоп-клиента.
- Используем словарь из GLOSSARY.md: Платформа, Тип, Объект, Свойство, Модуль, Действие, Манифест, Механизм, Набор изменений, Журнал, Трекер, Задача, Заметка, День, Категория.
- Решение «вся бизнес-логика на клиенте» зафиксировано в ADR 0001 и не пересматривается внутри этой спеки.

**Структура решения**
- Один серверный проект (веб-хост со всеми серверными папками внутри) и существующий проект тестов; отдельных C#-проектов платформы и модулей нет.
- Клиент разделён по папкам: `platform/` (универсальные компоненты, клиентская модель данных, Undo-стек, API-клиент, реестры вкладок и меню) и `modules/tracker/` (логика и экраны трекера). Все модули собираются в один клиентский бандл. Выделения в отдельные npm-пакеты в пилоте нет.
- Манифест модуля лежит рядом с модулем в клиентской части; сервер читает тот же файл при старте. Один деплой: сервер плюс клиент.
- Шаблонный демо-код `WeatherForecast*` удаляется, маршруты API добавляются в прокси Vite.

**Хранение**
- Postgres в `docker compose`; доступ через Dapper и Npgsql; миграции — пронумерованные SQL-скрипты через DbUp при старте. Для `jsonb` нужен небольшой обработчик типов.
- Три основные таблицы: типы (определения свойств, действий, перечислений, цветовых правил в `jsonb`), объекты (идентификатор, тип, родитель, владелец, порядок, значения свойств в `jsonb`), журнал (наборы изменений и записи «объект, свойство или операция, было, стало»). Отдельные таблицы для пользователей и refresh-токенов.
- Идентификаторы объектов генерирует клиент (UUIDv7). Удаление физическое, без корзины; журнал хранит полный снимок удалённого объекта.
- Фильтры представлений идут по `jsonb` с индексами по необходимости; дерево подгружается целиком, рекурсивные запросы применяются там, где нужен подграф.

**Модель данных платформы**
- Два уровня: Тип и Объект. Уровня «объявление экземпляра» (Iris) нет; значения по умолчанию хранятся в определении свойства типа.
- Объект имеет необязательного родителя, владельца и порядок среди соседей.
- Виды свойств: строка, многострочный текст, целое число, логическое, дата (`YYYY-MM-DD`), время (`HH:mm`), перечисление, ссылка на объект. Даты и время без часового пояса. Перечисления объявляются списком значений прямо у свойства в манифесте.
- Тип может быть абстрактным или запечатанным, иметь список допустимых дочерних типов, признак скрытия в основном дереве (`hiddenInTree`) и отметку механизма (`automation`).
- Действие объявляется в типе: идентификатор, название, параметры теми же восемью видами, `placements` из `automation`, `propertyGrid`, `contextMenu`. Действие всегда имеет объект-цель. Действия без `placements` — внутренние и доступны только из кода.
- Цветовые правила декларативны в манифесте типа (условие по свойству и значению, цвет).

**Манифест**
- Версионируемый JSON-файл описывает типы модуля, их свойства, перечисления, допустимые дочерние типы, действия и цветовые правила. Сервер при старте загружает типы в таблицу типов (обновляет по версии). Клиент получает типы через API. TS-обработчики действий и хуки привязываются по идентификаторам типа и действия.
- Пользовательские типы и редактор типов вне пилота, но таблица и серверная проверка рассчитаны на них.

**Сервер: контракты API (общий слой, без знания модулей)**
- Аутентификация: вход (e-mail, пароль) выдаёт access JWT (15 минут) и refresh-токен в `HttpOnly` cookie `SameSite=Strict` (около 30 дней); обновление access по refresh; выход отзывает refresh на сервере. Пароли хешируются `PasswordHasher`; полный ASP.NET Identity не используется; проверка JWT через JwtBearer. Минимальная длина пароля 8 символов.
- Сброс пароля: запрос по e-mail шлёт письмо со ссылкой; подтверждение ссылки задаёт новый пароль. SMTP настраивается в конфигурации; в разработке почту перехватывает Mailpit из `docker compose`.
- Администрирование пользователей (только роль «Администратор»): список, создание (e-mail, имя, пароль, роль), смена роли, отключение и включение входа, отправка ссылки на смену пароля. Пользователей не удаляют. Последнего администратора нельзя отключить или понизить. Самостоятельной регистрации нет. Первый администратор создаётся сидированием при первом запуске из настроек (user-secrets или переменные окружения).
- Загрузка данных: один запрос возвращает типы и все объекты пользователя.
- Применение набора изменений: операции создания (идентификатор, тип, родитель, порядок, значения), изменения свойства или перемещения (значения «было» и «стало»), удаления (снимок). Сервер применяет набор атомарно в транзакции и проверяет: объекты принадлежат пользователю, значения «было» совпадают с текущими (оптимистичная проверка), значения соответствуют определению типа, родитель существует и допустим для типа, тип не абстрактный. При любом нарушении набор отклоняется целиком с понятной причиной.
- Журнал: запись набора изменений (кто, когда, список операций с «было/стало» и снимками). Чтение журнала по объекту и «все мои изменения». Журнал только дописывается.
- Сервер не выполняет бизнес-логику модулей, хуки и действия.

**Клиент: платформа**
- Модель данных (`DataController`): после входа загружает все данные пользователя в память и работает с ними синхронно; поддерживает чтение дерева, создание, изменение, перемещение, удаление, наборы изменений, хуки до и после операций (с возможностью отменить), регистрацию типов и обработчиков действий.
- Одно действие пользователя — один набор изменений. Отправка набора на сервер, при отказе откат локальных изменений и показ причины; при расхождении «было» — предложение перезагрузить данные.
- Undo/Redo: стек в памяти вкладки (теряется при перезагрузке; журнал остаётся полным). Обратный набор изменений строится на клиенте и применяется без запуска хуков; сервер проверяет «было/стало», и при конфликте отмена отклоняется с сообщением.
- Клиентские пользовательские TS-скрипты вне пилота; хуки и обработчики модуля уже на TS в клиенте.
- Универсальные компоненты, рисуемые по метаданным типа: дерево (ленивая отрисовка узлов, перетаскивание с проверкой допустимых дочерних типов, контекстное меню из действий, иконки, цветовые правила, сортировка по порядку и названию); таблица свойств (группировка по категориям, правка на месте, редакторы по видам, только чтение, ссылки на объекты с выбором из дерева, кнопки действий); контейнер вкладок; главное меню; диалог параметров действия (поля по описанию параметров). Свои реализации на React, лёгкие библиотеки подключаются точечно (виртуализация, drag-and-drop).
- Реестры в `platform/`: виды вкладок (идентификатор, заголовок, компонент, одна или несколько копий) и пункты меню (путь, обработчик, условие по роли). Модули регистрируют записи из TS.
- Раскладка: фиксированные три панели с изменяемой шириной; открытые вкладки и ширины запоминаются в `localStorage` для каждого пользователя; чтение и запись обёрнуты в защиту от ошибок.
- Вкладки платформы: «Журнал» (записи выбранного объекта, переключатель «все мои изменения», только просмотр), «Автоматизация» (механизмы и их действия, у которых `placements` содержит `automation`), «Пользователи» (админка, пункт меню «Администрирование → Пользователи» только для администратора).
- Вход и выход, обновление access-токена и повтор запроса при 401; access-токен хранится только в памяти.

**Клиент: модуль Трекер**
- Типы: Задача, Заметка, Группа заметок, День, День-выходной, Месяц, Год, Категория, корневые группы («Задачи», «Текущие задачи», «Завершённые задачи», «Заметки»), механизм «Выделить текущий день», механизм быстрого доступа.
- Свойства Задачи: комментарий, приоритет (низкий, средний, высокий), время, «уведомить за (мин)», статус (не определён, завершена), внешняя ссылка, ссылка на внутренний объект, вид повтора (нет, каждый будний день, каждую неделю, каждый месяц), идентификатор повтора (скрытое). Дата задачи не хранится в ней: дата берётся из родительского узла дня.
- Свойства Заметки: комментарий, приоритет, статус, внешняя ссылка.
- Имена вычисляются: задача — «HH:mm — Имя» при наличии времени; заметка со статусом — «[Статус] Имя»; месяц — «MMMM, yyyy»; день — «dd.MM.yyyy, dddd».
- Действия: «Создать задачу» (на дне; параметры — название, необязательная категория, по умолчанию сегодня), «Завершить», «Отложить» (параметр — дата), «Перейти по внешней ссылке», «Перейти по внутренней ссылке», «Создать заметку» и «Создать группу заметок», «Добавить в быстрый доступ», «Убрать из быстрого доступа», «Выделить текущий день».
- Правила: узлы года, месяца и дня создаются клиентской логикой по требованию; «Завершить» ставит статус и переносит задачу в архив на ту же дату; «Отложить» переносит задачу в день выбранной даты; при переносе цепочка категорий воссоздаётся по названиям, а опустевшие категории удаляются; то же при удалении задачи.
- Повторы: включение создаёт реальные задачи на горизонт «до конца следующего месяца» (через узлы дней по требованию), «каждый будний день» пропускает выходные, для задачи выходного дня возвращает ошибку; повторы одного набора связаны идентификатором повтора и синхронизируют название, комментарий, ссылку, приоритет, время, порядок; дубли пропускаются; правки повторов идут с отключённым запуском хуков, чтобы избежать рекурсии; при каждом входе повторы достраиваются до горизонта; выключение удаляет созданные повторы.
- Быстрый доступ реализован механизмами-ссылками на заметку или группу, создаются и удаляются действиями, скрыты в основном дереве, видны на вкладке «Автоматизация»; при переименовании цели имя обновляется, при удалении цели механизмы удаляются.
- Уведомления: клиентский таймер раз в минуту проверяет задачи сегодняшнего дня, у которых есть время; с учётом «уведомить за N минут» показывает системное уведомление браузера (Notification API) при открытой вкладке; разрешение запрашивается один раз по действию пользователя.
- Стартовая структура создаётся клиентской логикой при первом входе, если корни отсутствуют.
- Цветовые правила: приоритеты задач и заметок (средний — оранжевый, высокий — красный), статус заметки «Завершена» — зелёный.

## Testing Decisions

Хороший тест проверяет внешнее поведение через шов, а не реализацию: не обращается к приватным функциям, не зависит от вёрстки и порядка вызовов внутри, читается как сценарий пользователя или клиента API. Выбраны три шва.

1. **Сервер, HTTP API.** Интеграционные тесты через `WebApplicationFactory` против настоящего Postgres (Testcontainers), миграции применяются как в обычном запуске. Проверяют контракт: вход, refresh, выход; сидирование первого администратора; админку пользователей; сброс пароля с перехватом письма в поддельном почтовом сервисе; загрузку типов и объектов; применение набора изменений (успех, отказ по «было», чужому владельцу, недопустимому типу или родителю, атомарность); журнал; роли. SQL, `jsonb` и миграции проверяются через этот шов, отдельных тестов на них нет.
2. **Клиент, `DataController` (TS).** Тесты на чистой логике, без DOM, с поддельным API-клиентом в памяти. Через этот шов проверяются наборы изменений, хуки, Undo/Redo (включая конфликт и отмену удаления), реестры, и вся логика трекера: стартовая структура, узлы по требованию, «Создать задачу», «Завершить», «Отложить», категории, повторы с достройкой, быстрый доступ, вычисляемые имена, расчёт времени уведомлений.
3. **Клиент, UI-компоненты.** Тесты Testing Library: дерево, таблица свойств, контейнер вкладок, главное меню, диалог параметров, вкладки «Журнал», «Автоматизация» и «Пользователи». Проверяют поведение пользователя (клик, ввод, перетаскивание, горячие клавиши), а не детали вёрстки.

Prior art: на сервере есть xUnit-проект с тестом контроллера шаблона, на клиенте настроены Vitest и Testing Library (`npm test`); других тестов нет, остальное создаётся с нуля. По правилам проекта после правок запускаются `dotnet test Nimrata.Core.slnx`, `npm test` и `npm run lint`, а новая логика покрывается тестами.

## Out of Scope

- Отчёт «Завершённые задачи» в Excel.
- Общие задачи, назначение исполнителей и совместная работа над одними объектами.
- Живые обновления между клиентами (SignalR), push-уведомления при закрытой вкладке и серверные задания по расписанию.
- Редактор типов и пользовательские типы в UI.
- Клиентские пользовательские скрипты на TypeScript, скриптовый движок.
- Тонкие права на отдельные объекты и свойства (только роли «Администратор» и «Участник» и владелец данных).
- Откат значения из вкладки «Журнал».
- Самостоятельная регистрация, подтверждение аккаунтов администратором, принудительная смена пароля при первом входе, удаление пользователей.
- Ленивая загрузка поддеревьев, корзина, часовые пояса, праздничный календарь.

- Сквозные e2e-тесты в браузере.

## Further Notes

- Пилот рассчитан на внутреннюю сеть или локальный запуск; публичное размещение потребует отдельной проверки безопасности (ограничения запросов на вход, HTTPS, политика паролей).
- Изменения каждого проекта фиксируются в его `CHANGELOG.md`, коммиты и комментарии на русском.
- Источники переноса: описания ядра Iris и модуля TaskTracker (локальные документы автора); их структура даёт ориентир, но не обязательна к точному воспроизведению.
