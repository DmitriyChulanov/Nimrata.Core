# Спецификация: синхронизация данных клиента и сервера

Термины — в `GLOSSARY.md` (Набор изменений, Журнал; новые: Синхронизация, Курсор, Подтверждённое состояние, Очередь неподтверждённых). Решение — `docs/adr/0006-sync-journal-cursor-push-offline.md` (создаётся в задаче 07). Опирается на ADR 0001 (логика на клиенте, сервер — хранилище с проверками) и ADR 0003 (скрытие отключённых расширений).

## Цель

1. Базовый механизм синхронизации, который понадобится для многопользовательской работы: правки уходят на сервер пакетами, изменения с сервера приходят без перезагрузки.
2. Защита от лавины мелких запросов: правки группируются по времени в обе стороны.
3. При изменении данных перерисовывается только тот элемент интерфейса, который они затрагивают.
4. Работа без сети: правки переживают перезагрузку вкладки и отсутствие связи, приложение открывается офлайн.

Сегодня данные строго свои у каждого пользователя (`owner_id`), поэтому «другой клиент» — это другая вкладка или устройство того же пользователя. Рабочие пространства и совместный доступ в эту работу не входят, но решения рассчитаны на них: группа рассылки и блокировка берутся по области видимости и потом переходят с пользователя на рабочее пространство.

## Решения

### Модель и сервер
- **Курсор.** Новое поле `changesets.seq bigint generated always as identity`. Курсор клиента — `seq` последнего известного набора. Новой колонки версии у `objects` нет: журнал (`changesets`/`changeset_entries`) — единственный источник изменений, удаления уже хранятся с `snapshot`.
- **Порядок фиксации.** Набор применяется под `pg_advisory_xact_lock` по пользователю, поэтому внутри области видимости порядок `seq` совпадает с порядком фиксации. Курсор не может проскочить незафиксированный набор с меньшим `seq`.
- **Идемпотентность.** `id` набора генерирует клиент (UUIDv7). Если набор с известным `id` приходит повторно, сервер ничего не применяет и возвращает прежний результат (`duplicate`). По тому же `id` клиент узнаёт своё эхо в push.
- **Конфликты — LWW.** У `update` (свойства) и `move` (`parent`, `number`) сервер больше не сверяет «было» и применяет новое значение. В журнал при этом пишется фактическое старое значение. Строгими остаются только структурные инварианты: объект существует, родитель существует и допустим по `allowedChildren`, нет цикла, singleton, расширение включено, у удаляемого нет детей вне набора, `create` с существующим `id`. Нарушение — отказ набора целиком. Каскадного удаления на сервере нет. Контракт `contracts/changeset` правится под это: категория `was`.
- **Пакетная запись.** Меняется `POST /api/changesets`: тело `{ changesets: [{ id, operations }] }`. Каждый набор применяется атомарно и независимо от остальных, отказ одного не откатывает другие. Ответ всегда 200 — список `[{ id, status: applied | duplicate | rejected, seq?, code?, detail? }]`. 4xx — только ошибки формата и авторизации.
- **Догон.** `GET /api/changes?since=N` → `{ toSeq, changesetIds, upserts: ObjectRecord[], deletes: id[] }`, в `upserts` — финальное состояние объектов. Если наборов после `N` больше порога (5000), ответ `{ resync: true }`. Видимость (включённые расширения) фильтруется так же, как в `GET objects`.
- **Согласованная загрузка.** Полная загрузка (объекты, типы) выполняется в одной транзакции `repeatable read` и возвращает `seq` снимка.
- **Push.** SignalR-хаб `/api/sync`, группа `user:{id}`. После фиксации сервис помечает пользователя «грязным». Диспетчер (`IChangeNotifier`) раз в 100 мс читает журнал из БД после последнего отправленного `seq`, собирает сообщение в формате догона и рассылает его группе. Источник истины — БД. Реализация внутри процесса, потом заменяема на `LISTEN/NOTIFY` или Redis backplane. Медленному клиенту вместо потока отправляется `resync`.
- **Подключение и отключение расширения** рассылается как событие `resync`.
- **Авторизация хаба.** JWT передаётся в query `access_token`, сервер берёт его оттуда только для пути хаба. После обновления токена клиент переподключается. В правиле `^/api` прокси Vite включается `ws: true`.
- **Настройки.** Секция `Sync:` — окно рассылки (100 мс) и порог resync (5000). Описаны в `docs/configuration.md`.

### Клиент
- **Два слоя.** Подтверждённое состояние (с сервера, до курсора) плюс очередь неподтверждённых наборов. Видимая модель — подтверждённое состояние с наложенной очередью. Входящие изменения применяются к подтверждённому слою, затем очередь накладывается заново (rebase). Подтверждённый свой набор переходит из очереди в подтверждённый слой.
- **Rebase без хуков.** При повторном наложении применяются записанные операции. Хуки отработали один раз, когда пользователь совершал действие.
- **Предсказуемый отказ и каскад.** Набор, структурно невалидный относительно нового подтверждённого состояния, сразу удаляется из очереди. Проверка — общим кодом контракта, тем же, что в `fakeApi`. Наборы, зависящие от отклонённого (например, правка созданного в нём объекта), удаляются каскадом. Пользователь получает одно сводное уведомление. `needsReload` и глобальная блокировка записи упраздняются.
- **Undo/redo.** Стек живёт только во вкладке и не сохраняется. Отмена — новый набор, обычным путём. Перед отменой клиент сверяет текущее значение с тем, которое ставил сам. Если не совпадает, запись undo отклоняется с уведомлением, чтобы молча не затереть чужую правку.
- **Адресные подписки.** `useObject(id)`, `useChildren(parentId)`, `useQuery(selector, deps)` на `useSyncExternalStore` с уведомлением только затронутых подписок. После каждого применённого набора (своего или входящего) хранилище вычисляет изменённые id и родителей. Дерево — мемоизированная строка на объект, PropertyGrid подписан на выделенные объекты. Глобальный `useData()` остаётся только там, где нужна вся модель.
- **SyncEngine.** Отдельный модуль сетевой части: отправка, push, догон, переподключение. Пишет в хранилище.
  - Окно отправки 200 мс от первой правки, не debounce.
  - Не больше одного запроса одновременно.
  - Не больше 500 операций в запросе, сверх лимита запрос делится; наборы не схлопываются.
  - Константы — в модуле синхронизации.
- **Офлайн — данные.** IndexedDB (своя тонкая обёртка), база по `userId`: снимок объектов и типов, курсор, очередь каждой вкладки (`tabId`).
  - Снимок пишет любая вкладка, только если её `seq` больше сохранённого.
  - Очередь закрытой вкладки (отпущен Web Lock) подхватывает открытая.
  - При старте сразу показывается снимок из кэша, затем догон.
  - Logout с непустой очередью — предупреждение, затем база удаляется.
  - Если вход истёк в офлайне, работа продолжается локально; после входа тем же пользователем очередь отправляется.
- **Офлайн — запуск.** Service worker через `vite-plugin-pwa` (`generateSW`): кэш собранных ассетов и `index.html`, `navigateFallback`, `/api` не перехватывается.
- **Вкладки.** У каждой свои соединение и очередь. Эхо между вкладками приходит через сервер, как от любого клиента.
- **Индикатор.** Компактный индикатор в шапке: «синхронизировано», «N неотправленных», «офлайн», «ошибка», подробности в подсказке. Иконка из реестра, токены, UI-кит. Предупреждения на `beforeunload` нет.
- **Журнал.** Открытая вкладка «Журнал» перечитывает первую страницу при сдвиге курсора.
- **Зависимости:** `@microsoft/signalr`, `vite-plugin-pwa`; dev — `fake-indexeddb`; тесты сервера — `Microsoft.AspNetCore.SignalR.Client`.

## Вне плана

Рабочие пространства и совместный доступ к объектам; несколько инстансов сервера (backplane); слияние текста и CRDT; сохранение undo между перезагрузками; синхронизация состояния UI вкладки (раскладка, открытые панели).
