# 03: SyncEngine — пакетная отправка

**What to build:** Отдельный модуль сетевой части берёт наборы из очереди и отправляет их пакетами с окном 200 мс, по одному запросу одновременно, с лимитом операций.

**Blocked by:** 02

**Status:** resolved

- [x] Модуль `SyncEngine` в `src/platform/` (сеть отдельно от хранилища); константы: окно 200 мс, лимит 500 операций
- [x] Окно отсчитывается от первой правки (не debounce); не больше одного запроса в полёте; новые наборы копятся
- [x] Деление пакета по лимиту операций без разрыва набора; наборы не схлопываются
- [x] Обработка ответа по статусам (`applied`, `duplicate`, `rejected`) → хранилище; при сетевой ошибке — повтор с экспоненциальной задержкой, очередь сохраняется
- [x] Тесты на фейковых таймерах: тысяча правок за окно — один запрос; порядок; повтор после ошибки; `npm test`, `npm run lint`; `CHANGELOG.md` клиента

## Comments

- Модуль — `nimrata.core.client/src/platform/sync/syncEngine.ts` (`createSyncEngine(api)` → `ChangesetTransport`), подключён в `DataController` по умолчанию, `createDirectTransport` удалён.
- «Тысяча правок за окно — один запрос» противоречит лимиту 500 операций: тысяча однооперационных наборов уходит двумя запросами по 500 сразу друг за другом (без нового окна); правки в пределах лимита — одним запросом. Так и проверено тестами.
- Повторяются: сетевая ошибка (не `ApiError`), 5xx, 401 (истёкший вход — очередь не теряется, нужно для 05), 408, 429; задержка 1 с · 2^n, не больше 30 с. Прочие 4xx (формат) отклоняют наборы пакета.
- Итог действия теперь ждёт окна отправки (≥ 200 мс). UI-тесты, проверявшие `api.changesets` сразу после действия, ждут его через `waitFor`; тесты «сбой 500 → откат» переписаны на отказ 422. Создание в дереве выделяет новый узел и открывает правку имени только после подтверждения (≥ 200 мс) — возможно, стоит разрешать `create` локально.
